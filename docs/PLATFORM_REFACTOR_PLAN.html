02
The premise

Goal & V1 scope

Turn TwistedFate from one Belote app into a shell + plugin platform. The shell owns everything common (table, cards, avatars, chat, lobby, auth, identity, friends, history). Each game is a plugin that contributes its rules engine, its bidding/action panels, its scoring display, and its AI.

V1 scope — same-deck, same-layout games only

Defer multi-deck and multi-seat-count abstractions until a real second-family game (Tarot, Bridge, Uno…) demands them.

Game Deck Players Layout What changes vs Belote
Belote (today) 32 4 (2v2) Current —
Simple Belote 32 4 (2v2) Identical No coinche / surcoinche, simpler scoring
Bigger Wins 32 4 (2v2) Identical Different rank order, no trump or all-trump
Coinche / Contrée 32 4 (2v2) Identical Auction-value bid model

What V1 does buy us

  • Plugin interface, registry, and lifecycle
  • Per-game match history + leaderboards
  • Game picker in lobby
  • Reusable shell for the next 3 games

What V1 explicitly skips

  • Variable deck sizes (no 52, 78, 108-special yet)
  • Variable seat counts (4-only)
  • Runtime federated module loading (build-time registry V1)
  • LLM personas (separate roadmap)

  • app/commands.ts hardcodes place_bid + play_card as the only actions — no abstraction over "game-specific action".

North star

Target architecture

A single platform shell that knows nothing about any specific game. Each game is a self-contained plugin bundle: rules engine, AI, per-game UI bits, per-game protocol encoding.

The shell never imports a game

All flow goes through the GamePlugin interface. Adding a 4th game requires zero shell changes.

Plugins never import each other

Each plugin is a leaf. Cross-game features live in shell (e.g. cross-game leaderboards).

05
The seam

The plugin contract

One interface, four collaborators: RulesEngine (pure logic) · AiPolicy (decisions) · PluginUiContributions (visuals) · PluginProtocol (wire encoding).

classDiagram class GamePlugin { +id : GameId +displayName : string +deck : DeckSpec +seating : SeatingSpec +rules : RulesEngine +ai : AiPolicy +ui : PluginUiContributions +protocol : PluginProtocol +messages : EventToMessageMap } class RulesEngine { +createInitialRound(deal, dealer) +legalActions(state, seat) +apply(state, action) +isRoundOver(state) +scoreRound(state) +isGameOver(totals, target) } class AiPolicy { +chooseAction(state, seat, persona) } class PluginUiContributions { +ActionPanel +ScoreLineRenderer +RoundSummaryDetails +EventBubbleRenderer } class PluginProtocol { +encodeAction(action) +decodeAction(wire) +encodeState(state, viewerSeat) +encodePrivate(state, viewerSeat) } GamePlugin --> RulesEngine GamePlugin --> AiPolicy GamePlugin --> PluginUiContributions GamePlugin --> PluginProtocol

TypeScript sketch

export interface GamePlugin<S, A, E> {
  readonly id:          GameId;             // "belote", "simple-belote", ...
  readonly displayName: string;
  readonly deck:        DeckSpec;           // V1 always Belote32
  readonly seating:     SeatingSpec;        // V1 always 4-2v2
  readonly rules:       RulesEngine<S, A, E>;
  readonly ai:          AiPolicy<S, A>;
  readonly ui:          PluginUiContributions<S, A, E>;
  readonly protocol:    PluginProtocol<S, A>;
}

export interface RulesEngine<S, A, E> {
  createInitialRound(deal: DealtHands, dealer: Seat):  S;
  legalActions(state: S, seat: Seat):                  readonly A[];
  apply(state: S, action: A):                          { state: S; events: readonly E[] };
  isRoundOver(state: S):                               boolean;
  scoreRound(state: S):                                RoundScore;
  isGameOver(totals: TeamTotals, target: number):      WinnerOrNull;
}

The shell GameSession only knows: deal cards → ask legalActions → dispatch apply → emit events → ask isRoundOver. It never sees a "bid" or a "trick".

Lock these before we touch code

Open questions for you

1 · Plugin loading model

Build-time import + static registry (my recommendation, V1) — simpler, shippable now. Or runtime federated module loading — lets games ship independently but adds infra cost.

2 · Naming

@cards/* for shell + @<game>-rules/* for plugins? Or @twistedfate/shell + @twistedfate/game-belote? Brand decision.

3 · Variant boundary

Is "Simple Belote" a separate plugin or a config flag on the Belote plugin? My take: separate plugin if it changes scoreRound or legalActions; config flag if only cosmetic.

4 · Persistence migration

Migrate existing matches table to add game_id (default "belote" for old rows). Confirm before I plan the SQL. One-shot or zero-downtime?

5 · The proof game — which one?

Of {Simple Belote, Bigger Wins, Coinche} — which validates the platform first?

  • Coinche — closest to Belote. Lowest risk, weakest platform stress test.
  • Simple Belote — strips features. Good for regression coverage of the rules engine.
  • Bigger Wins — different rank order, optional no-trump phase. Strongest platform stress test (forces the action-panel slot to render an empty state, exercises RankOrder param).
Awaiting decisions

Once these five lock, Phase 0 is one iteration of doc work and Phase 1 starts immediately after.
